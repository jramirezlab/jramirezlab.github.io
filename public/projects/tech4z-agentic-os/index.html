Overview#

TECH4Z Agentic OS is a multi-agent platform I designed, built, and operate as a solo engineer. It generates, evaluates, and delivers content across multiple channels — handling the pipeline from web intelligence gathering through LLM-driven editorial decisions to automated image generation and scheduled publishing.

The system runs on a multi-node Proxmox homelab with dedicated GPU passthrough per workload, a tiered LLM serving architecture, workflow automation via n8n, and infrastructure observability through Grafana and Prometheus. An owner-approval gate governs publishing decisions — the automation handles the heavy lifting, but final release authority stays with a human.

This is a working operational system with real output, not a demo or proof of concept. It is also a system that continues to evolve: the architecture described here reflects the core platform as built and validated, with areas noted where the design is advancing.

Key Engineering Decisions#

Dev/Prod Separation on Bare Metal#

Training and experimentation run on a dedicated development node. Production inference and generation run on separate nodes with their own GPU passthrough assignments. A failed training run or bad model swap never touches production output.

This mirrors how ML platform teams separate workloads at scale — I implemented it at homelab scale using Proxmox resource pools for isolation instead of Kubernetes namespaces. The principle is identical: blast-radius containment through workload segregation.

Tiered LLM Serving#

Heavy reasoning (32B parameter models) runs on dedicated GPU via Ollama. Lightweight inference (7B and 3B models) runs on separate CPU-bound instances. Every service references canonical network addresses, never localhost — the architecture is location-independent and could migrate to cloud endpoints without rewiring the orchestration layer.

This tiered approach keeps GPU resources focused on tasks that actually need them while handling simpler classification and formatting on CPU, reducing contention and improving throughput across the pipeline.

Multi-Agent Pipeline#

The content pipeline is a multi-agent system with defined roles and interfaces:

  1. Web intelligence — Crawl4AI gathers trending topics and competitive signals
  2. CEO Agent — An LLM (qwen2.5:32b on Ollama) evaluates inputs, decides what to produce, and generates downstream specifications
  3. Guardrail layer — Automated quality and policy checks before any content is generated
  4. Generation — ComfyUI executes image generation with locked prompt architectures and deterministic seeds
  5. Delivery — n8n workflows handle scheduling, platform-specific formatting, and publishing via APIs
  6. Owner gate — Human review and approval before content reaches external platforms

Each agent has a defined responsibility and interface contract. The CEO agent produces a specification; it doesn’t know or care how ComfyUI executes it. This separation of concerns makes the system testable and its failures diagnosable — when output quality drops, I can isolate whether the problem is in the intelligence gathering, the editorial decision, the generation parameters, or the delivery formatting.

Note: The orchestration architecture is actively evolving toward a more formally governed execution model with explicit policy enforcement and structured approval workflows. The core pipeline described here is operational and validated.

Backup and Recovery#

Every system state represents iterative engineering work — trained models, tuned prompts, workflow configurations, infrastructure state. Proxmox Backup Server runs on a ZFS mirror with nightly sync to offline storage. This design has been validated through actual hardware-failure recovery scenarios.

The backup architecture treats the entire platform as reproducible infrastructure: hypervisor configs, VM/LXC definitions, application state, and data are all captured. Recovery is documented in internal runbooks with tested procedures.

Technical Highlights#

GPU Passthrough: Blackwell Open Kernel Module Discovery#

When NVIDIA’s RTX 5070 Ti (Blackwell architecture) arrived, standard GPU passthrough into a Rocky Linux 9 LXC failed silently. Debugging this required two discoveries that had no existing documentation at the time:

  • Blackwell-generation cards mandate --kernel-module-type=open for the NVIDIA driver. The proprietary kernel modules don’t support passthrough on this architecture — a silent failure mode with no useful error output.
  • LXC GPU attachment requires eBPF cgroup device controllers. A clean pct stop resets the cgroup state correctly; a reboot inside the container does not, leaving the GPU device inaccessible until the container is fully stopped and restarted from the host.

This is the kind of undocumented launch-hardware problem that requires reading kernel source, testing hypotheses, and working without community answers. The fix is now understood, but at the time of discovery it required systematic driver and kernel debugging.

AMD GPU Reset Bug Mitigation#

The RX 7900 XTX exhibited the well-known AMD GPU reset bug under Proxmox — after a VM shutdown, the GPU enters a broken state and won’t reinitialize without a host reboot. I resolved this with the vendor-reset kernel module, which performs a proper device reset at the hardware level. Verifying the fix required repeated VM lifecycle testing to confirm the GPU reinitializes cleanly across shutdown/start cycles.

Deterministic Generation Architecture#

Content generation uses a locked four-layer prompt architecture with pinned seeds, resolutions, and model weights. Any output is reproducible from its parameters alone. Prompt and seed metadata are embedded in output files and committed to version control.

This isn’t just good practice — it’s how you debug generation quality regressions across model updates. When a LoRA fine-tune or base model change produces unexpected output, deterministic parameters let you isolate whether the regression is in the model, the prompt, the seed, or the generation settings.

What This Demonstrates#

  • Bare-metal GPU platform engineering — Multi-GPU passthrough with mixed NVIDIA/AMD vendors, kernel-level driver debugging on launch hardware, thermal management, and workload isolation using Proxmox virtualization
  • Agentic AI system design — Production multi-agent pipeline with defined agent roles, interface contracts, guardrail layers, deterministic outputs, and human-in-the-loop approval gates
  • Infrastructure automation at scale — n8n workflow orchestration with API integrations, tiered compute allocation, and autonomous batch operations under governed execution
  • Production reliability engineering — Backup/restore with validated recovery, observability stack, version-controlled configurations, dev/prod separation, and documented runbook discipline
  • Full-stack infrastructure ownership — Sole engineer across every layer: hardware selection and procurement, hypervisor clustering, GPU driver debugging, application deployment, LLM serving architecture, workflow automation, and operational monitoring
